In ycashd, a block is connected while holding one lock, and the vault acts inside it are applied one after another to a single overlay of state. Zakura is built differently: the transactions in a block are verified concurrently, each on its own, and only afterwards does the block reach contextual validation, where it's checked against the chain it extends.

Why order matters

A vault act can depend on an earlier act in the same block: a signer set changes its members, then a vault under that set is released. Checked in parallel, the second act would see the wrong set. The rules also include per-block rate limits and liveness counters, which only mean something when acts are counted in order.

What Kogany does

  • Scripts stay parallel. Signature checks, including the post-quantum ones, still run concurrently. They read a snapshot of the parent block's vault state, which the verifier waits for the same way Zakura already waits for other block information.
  • Acts run in sequence in contextual validation, applying a vault delta to the non-finalized state in transaction order.
  • The snapshot follows forks. It is keyed by the parent block's hash, not its height, so a reorganization never feeds one chain's state into another.
  • Every commit path computes deltas, including checkpointed blocks, and checkpoints stop before the vault epoch.

The cost

Waiting for the parent snapshot serializes part of the work on blocks after Vault activates. We don't yet know how much that costs, so it is one of the measurements in wave W4.
